# v2026.9.0 Release Announcement

Fortemi v2026.9.0 adds an authority-owned API for creating explicit note links
without opening the generated semantic graph to caller mutation. It also
aligns tag validation across the API and persistence layers while preserving
the existing five-level tag-path contract.

## Manual note links

`POST /api/v1/notes/{id}/links` now implements the
`manual-note-link-v1` contract:

- `{id}` identifies the source note and `to_note_id` identifies the target;
- `explicit` is the only caller-writable kind; `semantic` and `wiki` remain
  server-owned;
- score is optional or nullable, defaults to `1.0`, and otherwise must be a
  finite value from `0.0` through `1.0`;
- self-links and unknown request fields are rejected;
- initial creation returns `201`, an exact replay returns the same persisted
  identity with `200`, and conflicting attributes return `409`; and
- the operation deliberately emits no link event until an outbox-backed event
  contract is approved.

The generated OpenAPI artifact is contract revision `2`, version `2026.9.0`,
at SHA-256
`652bcce252719e5c0ced015beae02e41380c56dccaa5dc071d369b3ac6fdd858`.
It records the typed request and success bodies, RFC 9457 error responses,
bearer/write-scope requirement, source-resource role, target visibility check,
tenant transaction requirement, and the linked HotM consumer issue.

## Hosted isolation and database correctness

Hosted writes enter only through the transaction-scoped tenant boundary.
Fortemi checks source and target visibility together inside that transaction,
so callers do not receive an asymmetric existence signal for inaccessible
targets. Missing, archived, cross-tenant, and unauthorized targets leave no
link row behind.

PostgreSQL now owns the duplicate identity with a partial unique index over
`(from_note_id, to_note_id, kind)`. The insert path is atomic under concurrent
writers and returns the authoritative stored row. Exact retries converge on one
ID; different score or metadata does not silently overwrite the original.
Existing schemas are audited before migration, and ambiguous duplicate data is
rejected with a constant, identifier-free error rather than being deleted or
merged automatically.

## Stable redaction boundary

Manual-link request validation and debug output do not echo note identifiers,
submitted kinds, arbitrary metadata, note content, or database detail. This is
the same non-echoing boundary used by the hosted authorization tests and the
HotM typed consumer tests.

## Tag compatibility

The tag grammar is now enforced consistently across API validation, database
operations, ingest, and relationship lookup. Existing supported paths up to
five components remain valid, and regression coverage preserves legacy tag
relationships. The unrelated two-component restriction proposed in PR #58 was
not adopted.

## Consumer and platform claim boundary

HotM pins the exact producer commit and OpenAPI checksum through a typed,
compatibility-gated shared client. Primary UI and agent-tool exposure remain
documented exclusions. Its Linux x86_64, Linux arm64, and macOS arm64 immutable
consumer cells are explicitly deferred to release validation. Those deferrals
leave live mutation conformance unverified. Knowledge Shard and backup claims
remain limited to their previously published profile-qualified immutable
receipts; this release adds no suite-parity or portability evidence.

## Upgrade

Use the signed `v2026.9.0` release and its published checksums. Container users
should select the numbered release tag; ordinary branch validation does not
publish registry images.

The semantic-chunking panic reported in GitHub #56 remains fixed from
v2026.8.3. This release preserves its UTF-8-safe chunking and bounded job
recovery behavior.
