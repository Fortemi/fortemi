# Fortémi 2026.10.1

> **Version note.** The signed `v2026.10.0` tag exists, but it did not publish images or
> release assets: its release pipeline stopped at the documentation-shard freshness
> gate. 2026.10.1 is the first published release of this line and contains all of
> the 2026.10.0 changes plus the regenerated documentation shard.


Fortémi 2026.10.1 is the first stable cut of the hosted/Kubernetes delivery
line. It ships the split API, worker, MCP and migration topology for Helm and
Kustomize, publishes multi-architecture release images, adds a standalone MCP
image and a hosted KMS-capable image variant, and tightens MCP/OAuth behavior so
misconfigured deployments fail closed instead of silently using unsafe defaults.

The release also adds point-in-time memory export, OTLP traces and metrics, KMS
readiness in `/readyz`, path-bearing HTTPS issuers such as Keycloak realms, and
external-issuer MCP bearer-token verification through the API, and mapping of
external IdP groups and roles to Fortemi scopes (`FORTEMI_AUTH_CLAIM_POLICY_FILE`,
built on fortemi-auth `v2026.10.0`, contract 2.0.0). Managed PostgreSQL
deployments now require PostgreSQL 18.

## Upgrade notes: Docker bundle

1. Back up the existing database and `.env` before replacing the image.
2. Pull `ghcr.io/fortemi/fortemi:bundle-2026.10.1` or pin the release digest:
   `ghcr.io/fortemi/fortemi@<digest published with the release>`.
3. Keep `ISSUER_URL` set to the public OAuth/MCP URL. If the MCP server must
   call the API through a specific internal URL, set `MATRIC_API_URL` or
   `FORTEMI_URL`. The bundle sets `MCP_API_LAYOUT=bundle`, so a co-located API
   still works without a hosted fallback.
4. If you intentionally run anonymous MCP locally, set both
   `REQUIRE_AUTH=false` and `I_UNDERSTAND_NO_AUTH=true`. Hosted mode refuses
   anonymous MCP.
5. MCP OAuth clients must include the `mcp` scope. The bundle auto-provisions
   its introspection client with `mcp read write`; any manually registered MCP
   client should be re-registered with:

   ```bash
   matric-api admin oauth-client register --name "MCP Server" \
     --grant-types client_credentials --scope "mcp read write" --json
   ```

6. For browser authorization, review
   `FORTEMI_OAUTH_AUTHORIZE_OWNER_AUTH`. Self-hosted deployments still default
   to `none`; `api_key` or `trusted_header` is recommended. Hosted mode forces
   `disabled`.
7. Restart the bundle and verify `/health`, `/readyz`, and MCP protected
   resource metadata.

The bundle can now run as uid/gid `999`. Root starts remain supported; a first
non-root start against a volume from a root-run deployment may register a fresh
MCP client because the old credential file is root-owned.

## Upgrade notes: Kubernetes, Helm and Kustomize

1. Confirm PostgreSQL 18, Redis, and required extensions are available. Hosted
   deployments also need the migration/runtime role split and a KMS backend.
2. Register an MCP OAuth client with `mcp read write` and store
   `MCP_CLIENT_ID` / `MCP_CLIENT_SECRET` in the Secret used by
   `mcp.oauthClient.existingSecret` or the Kustomize MCP component.
3. Set the API image to `2026.10.1` for Community Edition, or
   `2026.10.1-hosted` for hosted single-tenant deployments that use AWS KMS or
   OpenBao Transit. Set the MCP image to `fortemi-mcp:2026.10.1`.
4. Configure MCP API reachability with `MATRIC_API_URL` or `FORTEMI_URL`, or
   `MCP_API_LAYOUT` only for co-located bundle/sidecar layouts.
5. For hosted mode, keep `FORTEMI_MULTI_TENANT=true`,
   `FORTEMI_OAUTH_DYNAMIC_REGISTRATION=disabled` or `admin`,
   `FORTEMI_OAUTH_AUTHORIZE_OWNER_AUTH=disabled`, `FORTEMI_KEY_PROVIDER`, and
   `FORTEMI_KMS_HEALTH_CANARY_SECS` as appropriate for the deployment.
6. Enable OTLP export with the standard `OTEL_*` variables only when a
   collector is ready. Use the Kustomize `otel` component or equivalent Helm
   env entries.
7. To derive scopes from IdP groups or roles, mount a JSON claim policy
   read-only and set `FORTEMI_AUTH_CLAIM_POLICY_FILE`. An invalid policy stops
   startup. See `docs/content/authentication.md` ("Mapping IdP groups and roles
   to scopes").
8. Roll out migrations first, then API, worker and MCP, and verify `/readyz`
   includes `key_provider` in hosted mode.

## Images

All release images are published as `linux/amd64` + `linux/arm64` indexes:

- `ghcr.io/fortemi/fortemi:2026.10.1`
- `ghcr.io/fortemi/fortemi:bundle-2026.10.1`
- `ghcr.io/fortemi/fortemi-mcp:2026.10.1`
- `ghcr.io/fortemi/fortemi:2026.10.1-hosted`

Verify the published digest with the release public key from the signed source
tree:

```bash
PUB=docs/security/cosign.pub
REF=ghcr.io/fortemi/fortemi@<digest published with the release>
cosign verify --key "$PUB" --insecure-ignore-tlog=true "$REF"
cosign verify-attestation --key "$PUB" --insecure-ignore-tlog=true \
  --type spdxjson "$REF" >/dev/null
cosign verify-attestation --key "$PUB" --insecure-ignore-tlog=true \
  --type slsaprovenance1 "$REF" >/dev/null
```

## Known issues

- #1163 remains open for tenant-bound `/api/v1/ws` and
  `/api/v1/ingest/stream`; hosted mode returns `401` without a valid bearer and
  `503` with one.
- #1165-#1169 track remaining hosted route-qualification gaps. Review
  `docs/deployment/hosted-route-qualification.md` before exposing a hosted
  tenant workflow.
- #943/#944 still track follow-up OAuth work. This release lands the fail-closed
  registration and authorization semantics described above, but hosted browser
  authorization remains disabled and self-hosted owner authentication should be
  explicitly configured before remote exposure.
