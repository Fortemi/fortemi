# v2026.8.3 Release Announcement

Fortemi v2026.8.3 is the customer-verification release for the semantic
chunking panic reported in GitHub #56 and tracked in Gitea #1100. Use this
release when retesting notes that previously stopped at `handler_panicked`
during embedding.

## What changed

The recovery change in v2026.7.22 prevented one failed embedding job from
wedging the queue, but it did not eliminate the chunking panic. The application
fix in commit `b6f528cd` is included in v2026.8.3 and addresses the root cause.

The earlier chunker used `str::lines()` and then reconstructed byte offsets by
adding each normalized line length. CRLF input therefore lost one byte per
line. After enough lines, a reconstructed range could land inside a multibyte
Unicode scalar such as U+2028 and panic during string slicing.

The corrected chunker:

- retains exact source byte spans across LF, CRLF, lone-CR, and mixed line
  endings;
- treats U+2028 and U+2029 as Unicode content rather than byte delimiters;
- adjusts chunk and overlap boundaries to complete UTF-8 scalar boundaries;
- uses checked slicing so invalid ranges fail safely rather than panicking; and
- preserves byte-exact reconstruction of the original input.

The focused semantic-chunking suite passes 61 tests, including the reproduced
CRLF plus U+2028 boundary case and additional non-ASCII regressions.

## Diagnostic privacy

The fix does not relax Fortemi's existing secret-redaction rules. Public issue
updates and failure output should include only bounded status and non-sensitive
location/class evidence. Do not publish note bodies, extracted PDF text, raw
database errors, credentials, tokens, or other user content.

## Upgrade and retest

```bash
docker compose -f docker-compose.bundle.yml pull
docker compose -f docker-compose.bundle.yml up -d
```

After upgrading, retry one previously affected PDF-derived note. Confirm that
the embedding job completes or reaches a bounded non-panic terminal result and
that later jobs continue to run. If the problem persists, share the release
version, job status, and redacted source location on GitHub #56; keep document
content private.

No new database migration, REST or event contract, or persistence-format change
is introduced by this patch. Knowledge Shard compatibility remains limited to
the exact `core-v1` producer/consumer cells and immutable receipts in the suite
contract registry; this is not a full-parity, complete-backup, or portability
claim.
