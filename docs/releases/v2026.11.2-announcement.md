# Fortemi 2026.11.2

This release fixes slow full-text search for deployments that run under forced
row-level security (Fortemi#1348). The GIN indexes added in 2026.11.1 could not
be used by hosted and external-OIDC runtime roles, because PostgreSQL only
pushes a search qual below a row-level security policy when its operators are
leakproof, and the text-search operators are not. Every lexical search for those
roles therefore still scanned and re-parsed the whole memory, about 2.7 seconds
regardless of term on a large corpus.

Lexical candidate admission now runs through `public.fts_admit_note_ids`, a
`SECURITY DEFINER` function that serves the title, stored text-search vector and
attachment arms from their GIN indexes. The outer statement keeps row-level
security on, so it remains a second check. The function enforces tenant
isolation itself and raises on an unset or malformed tenant. Results, tenant
isolation, archive scoping, tag filters and ordering are unchanged. Federated
search uses the same function for its title and content arms.

The function path is enabled by default only for deployments that are
single-tenant for lexical search: community mode and external-OIDC. In a
multi-tenant shared `public` schema the GIN postings span every tenant, so a
search's latency can scale with a term's frequency across tenants. No id, row,
count or content of another tenant is returned, but the timing channel is real,
so hosted multi-tenant deployments keep the direct row-level-security statements
unless an operator accepts it with `FTS_ADMISSION_SHARED_TENANT=accept`
(startup then logs an `ACCEPTED RISK` warning). Startup logs which path is
active and why.

Other search changes: the adaptive OR rerun is skipped when the exact hits
already fill the page, classification reuses the stored vector, and hybrid
search logs one info-level line of per-stage timings (never query text).

Security fixes: `url` 2.5.9 (RUSTSEC-2026-0592, stack overflow on nested `blob:`
URLs), `cookie` 0.18.3 (RUSTSEC-2026-0594, repeatable private cookie nonces in
forked processes), and builder image pins moved to buildx 0.38.1 and
docker-ce-cli 29.9.3 (CVE-2026-121541, Bake filesystem entitlement bypass).
RUSTSEC-2026-0543 (chrono, informational and unmaintained) is ignored for 30
days with a replacement tracked in Fortemi#1349.

Upgrade notes:

- The new migration `20261120010000_fts_admission_function.sql` creates the
  function. After deploy, verify its ownership and grant. The owner must be the
  migrator with BYPASSRLS (`SELECT proowner::regrole, prosecdef FROM pg_proc
  WHERE proname = 'fts_admit_note_ids'`), and the runtime role must hold EXECUTE
  (`SELECT has_function_privilege('<runtime role>',
  'public.fts_admit_note_ids(tsquery,text,text,text[],integer)', 'EXECUTE')`).
  No other role should.
- Run `ANALYZE attachment` after upgrading so the planner has current statistics
  for the attachment arm.
- Where the owner cannot bypass row-level security, or the function or its grant
  is missing, startup falls back to the direct statements automatically and logs
  the reason. The function never truncates: a call that would admit more than
  1,000,000 ids raises and that request is retried on the direct statements with
  identical results.

The workspace, MCP, Helm and AsyncAPI versions advance to 2026.11.2. The last
published release before this one is v2026.11.1.
