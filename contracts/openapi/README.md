# Fortemi OpenAPI contract

The supplemental native operation fixture under `fixtures/` qualifies
published Core2026.9.4 against native server2026.9.9 for authenticated FTS and
all advertised note mutations. It retains explicit semantic fallback and
personal-authorization boundaries; it does not change OpenAPI authority or
establish positive vector retrieval. See the fixture README and receipt.

`openapi.yaml` is the deterministic OpenAPI 3.1 consumer contract generated
from the same `ApiDoc` registration used by Fortemi's runtime
`/api/v1/operator/openapi.yaml` endpoint. `openapi.sha256` records its exact-byte digest.

Regenerate and verify the committed artifact:

```sh
scripts/ci/openapi-contract.sh generate
scripts/ci/openapi-contract.sh check
```

Handler annotation changes, including parameter descriptions, require regeneration
of both `openapi.yaml` and `openapi.sha256`. Keep the generated bytes and checksum
in the same change as the annotations. The
`tests::committed_openapi_artifact_is_current` test compares the production
generator's complete output byte for byte; a matching checksum alone does not
establish freshness. Review the generator's diff rather than editing generated
YAML or its checksum by hand.

OpenAPI `info.version` is the declared contract version, separate from the Cargo
package version and runtime build identity. Regenerating documentation does not
require changing these authorities. The publication receipt must bind the actual
producer commit and regenerated digest; retain historical consumer captures and
receipts under their original identities.

The route policy declares only `GET /api/v1/notes/{id}/similar` as
`ArchiveScoped`: profile-vector lookup stays in the selected tenant/archive.
The same path's `HEAD`, `GET /api/v1/entities/similar`, and
`GET /api/v1/graph/{id}` retain `CompleteCatalog`. Regeneration must preserve
these method-specific boundaries and bearer authorization. Consumers adopting
this producer revision must qualify selected-archive access, cross-tenant/archive
exclusion, hidden/deleted roots and candidates, and unchanged denial behavior on
the routes that retain complete-catalog admission. The Core route-policy,
profile-similarity HTTP, and database isolation fixtures supply producer checks;
consumer compatibility still requires each consumer's own fixtures and receipts.

Consumers pin the producer Git commit and fetch
`contracts/openapi/openapi.yaml` from that immutable revision. CI publishes
the same file with `openapi-contract-receipt.json`, which records the producer
commit, contract revision/version, stable path, and SHA-256 digest.

Every documented operation includes the global middleware's `429`
`application/problem+json` response using the shared `ProblemDetails` schema.
This gives consumers a schema-bearing response boundary for every operation
without inventing success payload schemas for handlers that have not declared
one. Existing typed success responses and body-free statuses remain unchanged.
